# x401 Draft 0.2.0: status and Stack implementation profile

Research date: 2026-07-22

## Executive conclusion

x401 is implementable today, but it is still an early draft rather than a
finished Internet standard. Stack can provide a production-quality
implementation **against the pinned Draft 0.2.0 wire protocol**, but should not
claim that x401 itself is final or broadly interoperable yet.

The strongest implementation strategy is:

1. pin the official `@proof.com/x401-node` SDK and its current wire names;
2. use signed OpenID4VP requests and short-lived, one-time nonces;
3. use an actual credential verifier rather than treating a decoded header as a
   verified proof;
4. issue short-lived, route-scoped verification tokens;
5. keep proof (`x401`) and payment (`HTTP 402` / `x402`) strictly separate;
6. expose the draft version and implementation limits in discovery metadata.

## What exists today

### Specification

- The [official specification](https://x401.proof.com/spec/latest/) is **Draft
  0.2.0**.
- It defines three base64url JSON HTTP headers: `PROOF-REQUEST`,
  `PROOF-RESPONSE`, and `PROOF-RESULT`.
- A proof request carries a Verifier-authored Digital Credentials API request in
  `credential_requirements.digital.requests`.
- OpenID4VP signed requests (`openid4vp-v1-signed`) are recommended. Unsigned
  requests are allowed but have weaker verifier/origin binding.
- Credential results can be returned inline or by an HTTPS reference.
- A verified Result Artifact can optionally be exchanged for a short-lived
  token through OAuth 2.0 Token Exchange.
- x401 explicitly does not define payment. Payment remains HTTP 402 plus a
  payment protocol such as x402.

Draft 0.2.0 is a breaking redesign of the earlier 0.1.0 shape. It removed the
old nested proof model and made the composed Digital Credentials request the
load-bearing object. The latest specification has also renamed early 0.2.0
terms such as `presentation_requirements` and `PROOF-REQUIRED`; implementations
must use the current `credential_requirements` and `PROOF-REQUEST` wire names.

### Official Node SDK

Proof publishes
[`@proof.com/x401-node`](https://github.com/proof/x401-node). Version `0.3.0`
implements the current Draft 0.2.0 data types, encoding, header parsing, Result
Artifacts, error objects, token objects, OAuth token-exchange forms, and
fixtures.

The SDK deliberately does **not**:

- compose or sign the OpenID4VP request;
- invoke a Credential Manager;
- verify credentials, issuer trust, revocation, predicates, or nonce freshness;
- mint or validate verification tokens.

Those are application/verifier responsibilities. Consequently, simply using
the official SDK is not sufficient to call an x401 gate secure.

### Credential verification

Proof also publishes
[`@proof.com/proof-vc-server`](https://github.com/proof/proof-vc-common), whose
`createVerifier()` verifies Proof SD-JWT VC presentations against development or
production trust roots. Its documentation explicitly leaves nonce comparison
to the caller, so Stack must enforce issued nonce, expiry, route/method binding,
and one-time consumption.

For credentials from other ecosystems, Stack needs a configured verifier
adapter that returns a cryptographically verified result and policy facts. A
generic `valid: true` JSON supplied by the requester is never sufficient.

## Maturity assessment

| Area | Current state | Stack treatment |
| --- | --- | --- |
| Wire format | Defined in Draft 0.2.0; official Node codec exists | Pin SDK/version and reject legacy names |
| OpenID4VP request | Defined; signed mode recommended | ES256 signed JAR with public JWKS |
| Credential verification | Format/issuer-specific | Proof verifier plus fail-closed external adapter |
| Replay protection | Required but storage design is implementation-specific | Firestore atomic nonce consumption; memory only for tests/dev |
| Result by reference | Defined, with SSRF and replay risks | HTTPS allowlist, bounded fetch, timeout, single-use reference |
| Reusable token | OAuth Token Exchange shape defined | Short-lived signed JWT scoped to route, method and requirement |
| Agent binding | Optional and still an open design area | Not implied by x401; SIWA/ERC-8128 remains a separate future layer |
| x402 composition | Explicitly separate; deeper binding is still open | Proof first, payment second; never treat either artifact as the other |
| Multi-endpoint composition | Open issue in the spec repository | One challenge/nonce per protected route |
| Standardization | Draft; no IETF/W3C final standard or IANA registration | Advertise `draft-0.2.0`, not “final standard” |

## Open protocol risks

The official repository still tracks unresolved design questions around
multi-endpoint proof requests, agent-asserted origins, autonomous delegation,
agent authentication, and proof/payment binding. Draft changes are therefore a
real compatibility risk.

Other operational risks are:

- header-size limits for inline presentations;
- SSRF and data exfiltration through `credential_result_uri`;
- nonce replay across serverless instances;
- accepting a credential without independently checking issuer trust,
  expiration, status/revocation, audience and DCQL predicates;
- accidentally charging through x402 before rejecting the x401 proof;
- storing raw identity claims or presentations in application logs.

## Stack support boundary

Stack's implementation profile is a reusable verifier/gate, not a credential
issuer or Credential Manager. It provides:

- official Draft 0.2.0 encoding and validation;
- signed OpenID4VP challenge construction;
- discovery and JWKS endpoints;
- direct and by-reference Result Artifact processing;
- Proof SD-JWT VC verification and a generic fail-closed verifier adapter;
- distributed one-time nonce consumption;
- `PROOF-RESULT` errors;
- OAuth token exchange and route-scoped verification-token retry;
- CORS exposure/allowance for all x401 headers;
- a sample protected route and reusable server library.

SIWA is not required for base x401 conformance and remains pending. When added,
it can bind the HTTP caller/agent to the verified human or organization proof;
it must not replace the credential verification performed by x401.

## Honest presentation language

Use:

> Stack implements a security-hardened verifier profile for x401 Draft 0.2.0,
> using Proof's official Node SDK and OpenID4VP credential verification.

Avoid:

> x401 is a finalized standard, or every x401 credential ecosystem is supported.
